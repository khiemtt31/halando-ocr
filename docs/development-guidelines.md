# Development Guidelines

Use these rules to keep the project understandable for junior and senior developers.

## Project Direction

- Keep the supported runtime local Docker Compose unless there is an explicit decision to support another runtime.
- Keep SQLite and local filesystem storage as the maintained path.
- Keep local demo auth simple and role-based.
- Prefer small changes with tests over broad rewrites.
- Update docs in the same change when behavior, commands, configuration, or flow changes.

## Code Layer Rules

- `app/api`: HTTP routing, dependency injection, request parsing, role checks, and response models.
- `app/services`: business rules such as upload validation, storage key creation, and audit behavior.
- `app/repositories`: SQLAlchemy queries and persistence only.
- `app/models`: database table definitions only.
- `app/schemas`: Pydantic request and response shapes only.
- `app/workers`: background processing and OCR pipeline only.
- `app/core`: shared runtime, settings, security, logging, errors, and time helpers.

When a route becomes hard to read, move business behavior into a service or repository instead of adding more route-local logic.

## Endpoint Checklist

When adding or changing an endpoint, check these items:

- Does it require the correct role with `require_roles(...)`?
- Does it enforce document ownership or admin access before returning data?
- Does it use a schema from `app/schemas` for public responses?
- Does it call services/repositories instead of embedding SQL or storage rules in the route?
- Does it return the existing error shape through `APIError` where possible?
- Does it record an audit event for important user actions?
- Does `docs/api.md` need to change?

## Database Checklist

When changing models, check these items:

- Update the matching Pydantic schema when API output changes.
- Update repository functions instead of duplicating query logic in routes.
- Update tests that depend on the model shape.
- Reset local `data/` because this project does not currently maintain migrations.
- Update docs if the data model or status lifecycle changes.

## Storage Checklist

When touching storage behavior, check these items:

- Keep storage keys generated by services rather than trusting client paths.
- Keep all local files under `LOCAL_STORAGE_ROOT`.
- Keep original files and OCR output files separate.
- Update `docs/application-flow.md` if storage behavior changes.
- Add or update storage tests when changing `app/services/storage.py`.

## Worker Checklist

When changing OCR behavior, check these items:

- Keep job claiming and status updates in repositories.
- Keep extraction logic in `app/workers/ocr_pipeline.py` or engine modules.
- Mark jobs failed with useful error messages when OCR cannot produce usable text.
- Update `docs/application-flow.md` when job statuses or OCR fallback behavior changes.
- Run the smoke test because it exercises upload, worker processing, text retrieval, search, and delete.

## Testing And Quality

Run these checks before considering a change complete:

```bash
.venv/bin/ruff check app tests
.venv/bin/python -m compileall app tests
.venv/bin/pytest
```

Use Docker verification when the change touches container files, OCR tooling, environment variables, or runtime paths:

```bash
docker compose up --build
docker compose logs -f api worker
```

## Clean Code Preferences

- Use clear names that match the domain: document, job, page, storage key, principal, audit event.
- Keep functions small enough to explain in one sentence.
- Avoid adding abstractions until two or more real call sites need them.
- Prefer typed dependencies and explicit return models.
- Keep comments rare and only use them to explain non-obvious decisions.
- Do not add production-only infrastructure unless the project scope changes.
